# 처리 절차와 고정 골조

## 0. 결과물 경로 잠금

파일 생성 요청이면 가장 먼저 결과물을 **네이티브 Google Docs**로 잠근다. 이 단계가 본문 초안보다 먼저다.

- Word/DOCX/PDF/Markdown 문서 생성 금지
- 채팅에 완성형 답변서 본문을 먼저 쓰는 것 금지
- DOCX를 만든 뒤 Drive에 올리는 방식 금지
- **Drive에서 템플릿 검색 금지**
- `1m3rgfQz_GqcyuijmqmRHKQq_PZKqER4II7A5PylHIqM` 문서 ID를 직접 읽는다.
- Google Docs 기준 문서 네이티브 복사 → 복제본 편집만 허용
- **복제본 ID/URL을 얻은 후에만 답변서 본문을 작성하여 문서에 넣는다.**
- copy/edit 권한 또는 기능이 없으면 파일 생성 중단. 다른 문서나 채팅 초안으로 우회하지 않는다.
- 최종 응답은 Google Docs URL만 반환

## 1. 입력자료 확인

기본 자료는 세 가지다.

1. 소비자기관 공문 또는 민원 접수 내용: 기관, 민원인의 실제 요구, 기관의 질문을 확인한다.
2. 결제 상세 정보: **기본적으로 계약기간과 이용상품을 확인한다.** 금액은 민원 쟁점일 때만 추가 사용한다.
3. 계약메모 전체: 핵심 경위, 민원인·임대인 입장, 당사의 실제 중재·조치, 최신 처리 상태를 확인한다.

사용자의 특별 요청은 선택사항이다.

## 1-1. 계약정보 잠금

`1. 계약 내용`의 계약기간과 이용상품은 해석 대상이 아니라 **원문 전사 대상**이다.

1. 결제 상세 정보에서 대상 계약의 `계약기간`, `이용상품`을 찾는다.
2. 두 값을 원문 그대로 `contract_source.raw_excerpt`에 옮긴다.
3. `contract_period`, `product_name`은 `raw_excerpt`의 문자열과 정확히 같게 쓴다.
4. 계약메모의 날짜나 다른 계약명을 이용해 보정하지 않는다.
5. 대상 계약이 여러 개라 어느 계약인지 확정할 수 없으면 여기서 멈추고 확인한다.

사용자가 계약 상세를 텍스트로 직접 적어 준 경우에는 `contract_source.type`을 `user_explicit`으로 둘 수 있다.

## 2. 원자료 판독

다음 다섯 가지로 내부 정리한다.

- `민원인 주장`
- `임대인 설명`
- `확인 사실`
- `당사 조치`
- `미확인/충돌`

같은 사실이 반복되면 하나만 남긴다. 행정성 로그, 담당자 변경, 중복 문의 등 결론에 영향이 없는 기록은 제외한다.

## 3. 관련성 필터

본문에 넣는 사실은 아래 중 하나를 충족해야 한다.

- 민원인이 왜 문제를 제기했는지 설명함
- 결론에 영향을 주는 핵심 경위임
- 당사가 실제로 어떤 노력을 했는지 보여줌
- 임대인의 현재 확인된 입장을 보여줌
- 당사 역할과 권한의 한계를 설명하는 데 필요함
- 공문이 명시적으로 답변을 요구함

위 조건에 들지 않으면 사실이어도 본문에서 제외한다.

특히 다음은 자동으로 넣지 않는다.

- 결제 상세의 세부 금액 구성
- 정상 반환된 보증금
- `수리 완료 기록이 확인되지 않음` 같은 단순 증빙 공백
- `회신일 현재 ~ 확인되지 않음` 같은 불필요한 미완료 상태
- 전대차동의서 등 제출 여부의 세부 상태
- 협의 과정에서 나온 조건부·가정적 반환 발언
- 내부 처리명 `CS 지원금`, `CS 보상`

## 4. 작성 전 확인 게이트

다음 중 하나라도 해당하면 초안 전에 필요한 질문만 짧게 묶어 한다.

- 공문/결제 상세/계약메모 중 답변에 필요한 자료가 빠짐
- 민원인의 요구가 불명확함
- 임대인의 현재 입장 또는 실제 지급 상태가 충돌함
- `제안/예정/완료` 상태가 불명확함
- 공문이 별도 항목별 답변을 요구함
- 계약기간·이용상품 외 계약 항목을 넣을 필요가 있음

추가 계약 항목은 반드시 사용자에게 먼저 제안한다.

> 이 사안은 ○○ 확인이 중요해서 △△ 항목도 넣으면 어떨까요?

## 5. 단일 사용 사실 맵

초안 전에 핵심 사실마다 사용할 위치를 하나만 정한다.

- 민원인의 주장·요구 → 2항
- 민원인의 계속 이용, 퇴실 등 핵심 경위 → 2항
- 당사의 연락·환불 협의·중재 → 3항
- 임대인의 반환 의사·거절 사유 → 3항
- 당사 현금 보상 등 실제 조치 → 3항
- 당사 권한 한계 → 3항
- 향후 확인·중재 → 3항

같은 사실을 2항과 3항에 동시에 쓰지 않는다.

## 6. 문서 골조

### 1. 계약 내용

기본 두 행만 사용한다.

- 계약기간
- 이용상품

주소, 결제금액, 계약일자, 보증금 등은 사용자 동의 없이 추가하지 않는다.

### 2. 민원 내용 및 확인 결과

2~5개의 짧은 문단으로 쓴다.

- 첫 문단: 민원인이 무엇을 문제 삼고 무엇을 요구하는지
- 이후 문단: 결론에 필요한 실제 경위만 시간순으로

`당사가 임대인에게 연락했다`, `현금 보상했다` 등 당사 조치는 원칙적으로 3항에 둔다.

### 3. 민원 관련 당사 입장 및 조치

2~4개의 짧은 문단으로 쓴다. 정확히 네 문단을 채우기 위해 내용을 반복하지 않는다.

가능한 순서:

1. 당사가 실제로 한 연락·협의·중재와 임대인의 현재 확인된 입장
2. 실제 회사 보상 또는 별도 조치가 있으면 외부용 문장으로 풀어 쓴 내용
3. 환불·배상 등에 대한 당사 역할과 권한의 한계 — 부드러운 문장
4. 필요한 경우 리스크 쟁점의 사실확인 및 향후 중재

회사 보상 권장 문장:
> 민원인이 이용 과정에서 겪은 불편을 고려하여, 당사는 이용 수수료 40,590원을 현금으로 보상하였습니다.

역할 한계 권장 문장:
> 해당 이용대금은 입주 확인 후 임대인에게 정산된 상태입니다. 이에 반환 여부는 임대인과의 협의를 통해 조정이 필요한 사항으로, 당사에서 직접 반환하기는 어렵습니다.

후속 중재 권장 문장:
> 당사는 민원인의 반환 요청이 원만히 협의될 수 있도록 임대인과의 중재를 이어가겠습니다.

임대인의 입장이 여러 번 바뀌었으면 협의 과정 전체를 나열하지 않는다. **현재 회신에 필요한 확정적·실질적 입장만** 적는다.

## 7. 리스크 쟁점 표현

전대·등록 권한·적법성 등은 법률 판단처럼 쓰지 않는다.

기본 표현:
> 민원인이 제기한 임대 권한 관련 내용에 대해서도 당사는 임대인에게 사실관계 확인을 요청하였습니다.

공문이 구체적인 자료 제출 여부를 묻지 않는 한 `자료가 없다`, `동의서를 못 받았다`, `무단 전대다` 같은 표현을 본문에 넣지 않는다.

## 8. 문장 회귀 체크 — 파일 생성 전 필수

아래 표현이 있으면 초안을 다시 쓴다.

- `CS 지원금`, `CS 보상`, `CS` 내부용어
- `이용대금 ○원(임대료 ○원, 관리비 ○원, 청소비 ○원)` 식의 세부 구성 나열
- `당사가 보관하고 있지 않습니다`
- `임의로 회수하거나`
- `당사가 전액 반환을 확정할 수는`
- `회신일 현재 ... 확인되지 않았습니다` 등 불필요한 미확인 상태

## 9. 결과 전달

사용자가 텍스트만 요청하면 채팅으로 답변서와 간단 검수만 제공한다.

파일 결과는 **네이티브 Google Docs만** 사용한다.

1. `case-data.json`을 만들고 계약정보·금액·관련성·문장 가드를 검증
2. Drive 검색 없이 `references/google-docs-template.md`의 고정 document ID를 직접 읽어 SpaceV 로고와 고정 구조를 확인
3. Google Drive 네이티브 copy 기능으로 기준 문서를 복제하고 **복제본 URL 확보 전에는 사용자 채팅에 본문을 출력하지 않음**
4. 복제본만 편집하고 원본의 로고·페이지·표·서식 구조는 유지
5. 현재 사건 값으로 수신인·제목·계약정보·2항·3항·발신정보를 교체
6. 완성본을 다시 읽어 로고, 2행×2열 계약표, 계약정보 일치, 금지 문장, 템플릿 사건 잔존 여부를 검증
7. **Google Docs URL만 반환**

DOCX/Word를 생성하거나 업로드하는 fallback은 사용하지 않는다. 네이티브 copy/edit 기능이 없으면 양식을 재작성하지 말고 필요한 Google Drive 권한 또는 기능이 없다고 알린다.


## Native-copy fidelity requirement

Before this workflow starts, apply `native-copy-fidelity-gate.md`. Native file copy must succeed and the copied document must pass the structural clone signature before any response prose is drafted. A blank/recreated Google Doc is always a failure.
